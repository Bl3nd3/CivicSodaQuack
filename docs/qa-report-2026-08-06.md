# CivicSodaQuack — Exploratory QA Session Report

**Date:** 2026-08-06 (revised same day — see *Revision history*)
**Build under test:** `v0.7.0-1-g35515b0` (main @ `35515b0`)
**Platform:** macOS (darwin 25.5.0), arm64
**Method:** Unscripted end-to-end exercise — first-time MCP install, catalog discovery on an unfamiliar portal, config authoring, full sync, and analytical querying.

**Defect status:** 1 of 7 fixed (P2-1). P1-1 and P1-2 remain open and are the two that matter.

---

## Executive summary

The core product works. A first-time operator took `csq` from a cold install to 3.17M rows of live county data queryable through an AI agent in a single session, with zero sync failures and no code changes required to target a portal the tool had never seen. The portal-agnostic architecture is the standout result — see Successes.

Seven defects surfaced; **P2-1 has since been fixed (`68ad3f2`)**. Two remain worth fixing before wider MCP adoption:

- **P1-1** — the MCP server takes an **exclusive write lock** on portals it only ever reads, blocking concurrent `sync` and any second server. The error message's suggested remedy (`--no-lock`) does not work.
- **P1-2** — `list_datasets` **fabricates a `table_name`** for datasets that were never synced, and silently omits the one field that would reveal this. This is a direct hallucination vector for the agents this tool exists to serve.

Both are small, well-localized fixes. Neither is architectural.

## Successes

**1. Portal-agnostic design held up under a real test.**
The single most valuable result. The session began against `data.cityofchicago.org`, determined mid-session that Chicago publishes no incarceration data, and pivoted to `datacatalog.cookcountyil.gov` — a portal the tool had never been pointed at. Discovery, config, sync, and MCP serving all worked with **no code changes and no per-portal special-casing**. This is the product thesis, and it is validated.

**2. Sync was clean at scale.**

```
[csq] summary: 5 ok, 0 failed, 0 aborted, wall 10m38.400382417s
```

| table | rows | expected | match |
|---|---:|---:|:--:|
| `initiation` | 1,228,260 | 1,228,260 | ✅ |
| `dispositions` | 1,080,014 | 1,080,014 | ✅ |
| `intake` | 528,111 | 528,111 | ✅ |
| `sentencing` | 305,884 | 305,884 | ✅ |
| `diversion` | 29,421 | 29,421 | ✅ |
| **total** | **3,171,690** | | |

Every table matched its upstream SODA `count(*)` exactly. Concurrency worked — datasets interleaved in the log and the 10m38s wall clock is roughly the longest single dataset, not the sum.

**3. `query_sql` read-only enforcement is well-designed.**
Wrapping user SQL in `BEGIN TRANSACTION READ ONLY` on an in-memory host with portals `ATTACH`ed `(READ_ONLY)` is the right call — engine-enforced rather than regex-filtered, which is the usual (and bypassable) approach. `tools_query_sql.go:37` documents the reasoning clearly.

**4. Sensible guardrails.**
`assertIsCSQDB` (`pools.go:108`) rejects arbitrary DuckDB files with a clear message. Result caps (1000 rows / 1MB / 30s) are appropriate for agent consumption. `${ENV}` expansion fails loudly rather than silently sending an empty token.

**5. Lock *detection* works correctly.**
The advisory `flock` fired exactly as designed and named the offending file. Only the suggested remedy is wrong (P1-1).

## Defects

### P1-1 — MCP server takes an exclusive *write* lock on read-only portals

**Severity:** High — blocks the primary multi-process workflow.

**Repro:**
1. `csq mcp --db chicago=data.cityofchicago.org.duckdb` (read-only; no `--config`)
2. In another shell, any second process touching that file:

```
csq mcp: portal database is locked by another process:
  data.cityofchicago.org.duckdb.lock
  (pass --no-lock to bypass, or --lock-wait <duration> to retry)
```

3. Follow the advice — `--no-lock` — and it fails anyway, worse:

```
IO Error: Could not set lock on file "data.cityofchicago.org.duckdb":
Conflicting lock is held in .../csq (PID 28092) by user jasper.
However, you would be able to open this database in read-only mode...
```

**Root cause:** `internal/mcpserver/pools.go`. Line 61 correctly `ATTACH`es each portal `(READ_ONLY)` to the in-memory host. But line 50 *also* opens a separate per-portal handle via `openDB(spec.Path)`, and `openDB` (line 95–105) calls `sql.Open("duckdb", path)` with **no `access_mode`** — i.e. read-write. That handle takes DuckDB's exclusive file lock.

The code comment at `pools.go:91–94` is explicit that this is read-write, and `pools.go:14–18` notes the per-portal pools "only run hardcoded internal queries (list/describe/search)" — all reads. So the write access is not needed for the read-only configuration.

**Impact:**
- Cannot `csq sync` a portal while an MCP server serves it — which is the steady state once an agent is configured.
- Cannot run two MCP servers over the same portal (e.g. one stdio for a local agent, one HTTP for a remote one).
- `--no-lock` is actively misleading: it skips `csq`'s *advisory* lock but DuckDB's lock sits underneath, so the flag cannot do what its error message promises. An operator following the hint gets a more confusing failure than if they hadn't.

**Suggested fix:** open the per-portal pool with `access_mode=read_only` when that portal has no `--config` (i.e. no write tools), matching the `ATTACH` mode. DuckDB permits unlimited concurrent cross-process readers, so this makes the common case fully concurrent. Where `--config` *is* supplied, read-write is genuinely required and the current lock behaviour is correct.

**Secondary fix:** amend the lock error message so it does not recommend `--no-lock` for a case that flag cannot resolve.

### P1-2 — `list_datasets` fabricates `table_name` for never-synced datasets

**Severity:** High — hallucination vector in an agent-facing tool.

**Repro:** attach a portal DB that has had `csq catalog` run but never `csq sync`, then call `list_datasets`.

Observed on the Chicago DB: **2,010 entries returned, every one with a populated `table_name`** — against **zero** actual data tables. Only three `_csq` bookkeeping tables existed, and `_csq.sync_runs` was empty, confirming no sync had ever run.

**Root cause:** `internal/mcpserver/tools_list_datasets.go:113–118`:

```go
if table.Valid {
    summary.TableName = table.String
} else {
    summary.TableName = strings.ReplaceAll(id, "-", "_")   // ← invented
}
```

When the `LEFT JOIN` against `_csq.sync_runs` misses, the code synthesises a plausible-looking table name from the dataset ID. The one field that would betray this — `row_count` — is declared `json:"row_count,omitempty"` (line 25), so a `NULL` count is **omitted from the JSON entirely** rather than emitted as `null`.

**Impact:** The tool description reads "List datasets **available** across attached portal DuckDB files." An LLM agent receives 2,010 entries each carrying a concrete `table_name` and no contradicting signal, and will confidently emit `SELECT * FROM dpt3_jri9` — which fails with a binder error. This is precisely the failure mode an agent-facing data tool must not have: it is not a missing feature, it is the tool asserting something false. During this session it caused a real detour before the discrepancy was caught by cross-checking `duckdb_tables()`.

**Suggested fix:** emit `table_name: null` (or omit the entry) when no successful sync exists, and add an explicit `synced: bool`. Drop `omitempty` from `row_count` so `null` is visible. Consider a `synced_only` filter defaulting to `true`.

### P2-1 — `_csq.catalog.updated_at` is always NULL (wrong JSON key) — ✅ FIXED

**Severity:** Medium — silent data loss; masked by a passing test.
**Status:** Fixed in `68ad3f2`. See *Resolution* below, which includes a correction to this entry's original impact assessment.

**Evidence:** across both portals, every catalog row has a NULL `updated_at`:

| portal | catalog rows | non-null `updated_at` |
|---|---:|---:|
| Chicago | 2,010 | **0** |
| Cook County | 808 | **0** |

The CLI reflects it — `csq catalog` printed `-` in the `UPDATED` column for every row on both portals.

**Root cause:** `internal/socrata/catalog.go:80` declares:

```go
RowsUpdatedAt string `json:"rowsUpdatedAt"`
```

The live `/api/catalog/v1` resource object contains **no `rowsUpdatedAt` key**. Actual keys are `updatedAt` and `data_updated_at`:

```
resource keys: [... 'createdAt', 'data_updated_at', ... 'metadata_updated_at', 'name', ... 'updatedAt']
  'rowsUpdatedAt': None
  'updatedAt':       2026-08-06T20:24:56.000Z
  'data_updated_at': 2026-08-06T20:24:56.000Z
```

The parse block at `catalog.go:135–138` is correct; it is simply never reached because the tag never matches.

**Why the test suite misses it:** `internal/socrata/catalog_test.go:29` builds a hand-written fixture containing `"rowsUpdatedAt": "2024-01-15T00:00:00.000"`, and lines 63–66 assert `UpdatedAt` is non-nil. `TestFetchCatalog_Paginates` **passes**. This is fixture drift — the test validates the parser against a response shape the API does not produce.

**Impact:** `updated_at` is the natural field for deciding what to re-sync and for surfacing dataset staleness — it was unavailable for either. Note `row_count` being NULL is *by design* (documented at `catalog.go:22`), so it is not a defect; `updated_at` is.

**Suggested fix:** change the tag to `data_updated_at` (preferred — it tracks data rather than metadata edits) or `updatedAt`. Add a smoke test that runs against a recorded *real* API response rather than a hand-authored fixture.

#### Resolution — `68ad3f2`

`rawCatalogEntry` now reads `data_updated_at`, falling back to `updatedAt` and then `rowsUpdatedAt` (so a `/api/views/` payload still resolves) through a new `parseCatalogTimestamp` helper.

**The field choice turned out to matter more than the bug.** Measured across a 100-dataset Chicago sample:

| comparison | count |
|---|---:|
| `updatedAt` == `data_updated_at` | 52 |
| `updatedAt` **later than** `data_updated_at` | 48 |
| `updatedAt` earlier | 0 |

`updatedAt` is `max(data_updated_at, metadata_updated_at)`. Dataset `2ft4-4uik` has data frozen since **2011** but an `updatedAt` of **2015**, purely because someone edited its description. The obvious one-word fix — pointing the tag at `updatedAt` — would have cleared the NULLs while silently reporting metadata churn as data freshness. Worth noting as a case where the cheap fix was the wrong one.

**Verified live, not only in tests** (the original test also passed while broken):

| portal | before | after |
|---|---:|---:|
| Cook County `_csq.catalog.updated_at` populated | 0 / 808 | **808 / 808** |

**Fixture drift addressed at the cause.** The fixture now mirrors a real payload. `TestCatalogTimestampPrecedence` pins the field order so a reorder fails loudly, and `TestFetchCatalog_LiveResponseShape` replays a trimmed real response including the frozen-dataset case.

**Correction to this entry's original impact claim.** The version of this report issued before the fix asserted that a working `updated_at` "would have immediately flagged that all five Cook County datasets were frozen." **That was wrong, and the fix disproves it.** Those five datasets were abandoned by the SAO on 2024-12-30 with coverage ending 2024-11-30, yet now report `updated_at` of **2026-04-02** — the portal republished unchanged rows and the timestamp moved with it.

So the fix closes the metadata-edit hole but not the republish hole. `data_updated_at` is a real improvement and the correct field, but it is still not a reliable staleness signal on its own; the dataset's own description remains the only dependable source. This narrows P2-1's practical benefit from what was originally claimed, and the README caveat was rewritten to match rather than left overstating the outcome.

### P2-2 — `list_datasets` has no pagination or result cap

**Severity:** Medium — agent ergonomics.

**Repro:** call `list_datasets` with no filters on a 2,010-entry catalog.

**Observed:** a **351,820-character** response — large enough to exceed the agent's tool-result budget outright. `ListDatasetsArgs` (`tools_list_datasets.go:14`) exposes only `portal` and `category`; there is no `limit` or `offset`.

**Impact:** the tool is unusable in its default, no-argument form on any real portal — which is exactly how an agent will first call it. Notably `query_sql` *is* capped at 1000 rows / 1MB; `list_datasets` should inherit the same discipline.

**Suggested fix:** add `limit` (default ~100) and `offset`, and return a `total` count so the agent can page deliberately.

### P3-1 — `--dry-run` does not enumerate what it would sync

**Observed:** the entire output for a five-dataset config was:

```
[csq] dry-run: would sync 5 datasets
```

**Impact:** the count confirms selectors resolved but not *which* datasets matched — the main thing a dry run should answer. With glob selectors (`category:`, `tag:`) this gap is more consequential, since a mistyped pattern silently matches the wrong set.

**Suggested fix:** list id, resolved table name, and mode per dataset.

---

### P3-2 — no `--version` flag

**Observed:** `./csq --version` → `unknown subcommand "--version"`.

The version is compiled in and reachable (`serverInfo.version` reported `v0.7.0-1-g35515b0` over MCP), but there is no way to read it from the CLI. This matters for bug reports — establishing the build under test required an MCP handshake.

**Suggested fix:** `csq --version` / `csq version`.

---

### P3-3 — unset `${ENV}` in `app_token` is a hard validation failure

**Observed:**

```
csq sync: validate "...yaml": app_token: ${ENV} reference expanded to
empty string (env var unset?)
```

Failing loudly is defensible and the message is good. But since anonymous access is legitimate (just rate-limited), a config committed with `app_token: ${SOCRATA_APP_TOKEN}` cannot be run by a colleague who hasn't set the variable — the workaround is to comment the line out, which is easy to commit by accident.

**Suggested fix:** consider a warn-and-continue path, or document `app_token: ${SOCRATA_APP_TOKEN:-}` style optional syntax.

## Recommendations

**Before wider MCP rollout**
1. Fix **P1-1** — open read-only portals `access_mode=read_only`. Unlocks concurrent sync + serve, the expected steady state.
2. Fix **P1-2** — stop inventing `table_name`; add `synced`. Highest-leverage correctness fix for agent consumers.
3. Correct the lock error message so it stops recommending a flag that cannot help.

**Near term**
4. ~~Fix **P2-1** (`data_updated_at`) and re-point the catalog test at a recorded real response.~~ **Done — `68ad3f2`.** The remaining half of this item still stands: audit the other struct tags in `internal/socrata` against the live API. Where one field name drifted, others may have, and the same class of fixture would hide them equally well.
5. Add `limit`/`offset` to `list_datasets` (**P2-2**), matching `query_sql`'s existing caps.

**Testing process**
6. **The fixture-drift pattern is the most transferable finding.** A green unit suite asserted behaviour that is broken against the real API. Recommend a small contract-test tier that runs against recorded live responses, refreshed periodically — the parser was correct; only the assumed response shape was wrong, and no amount of unit testing against hand-written fixtures would ever catch that.
7. Add a multi-process concurrency test (serve + sync simultaneously). P1-1 is invisible to single-process tests, which is likely why it survived.
8. Consider surfacing upstream data-quality signals. Cook County's `sentence_date` ranges to the year **2921**, and `race` carries both `HISPANIC` and `White [Hispanic or Latino]` as distinct values. Not `csq` bugs — but an agent querying this data will produce confidently wrong answers, and a `csq doctor`-style column profile would help consumers catch it.

**Not yet covered** — snapshot/fetch, write tools, HTTP transport. Recommend a follow-up session.
